# Production deployment & ops notes

Checklist for Diamond Steam Car Wash (`dscw`) when you deploy to a live host, plus what to keep in mind for future features.

Admin login after seeding: `admin@diamondsteamcarwash.com` / `password` — **change this immediately** in production.

---

## 1. First-time production deploy (do this once)

### Server requirements
- PHP **8.3+** with extensions Laravel needs (`mbstring`, `openssl`, `pdo`, `tokenizer`, `xml`, `ctype`, `json`, `bcmath`, `fileinfo`, `gd` or `imagick` recommended for images)
- Composer 2
- Node.js 20+ (only needed to build front-end assets; can build locally and upload `public/build`)
- MySQL/MariaDB (preferred in production) or PostgreSQL — avoid SQLite on shared hosting for live traffic
- HTTPS domain pointing at the app’s `public/` directory (document root must be `public/`, not the project root)

### Create the app on the server
```bash
# From the project root on the server
composer install --no-dev --optimize-autoloader
cp .env.example .env
php artisan key:generate
```

If you build assets on the server:
```bash
npm ci
npm run build
```

If you build locally, upload the generated `public/build/` folder (and `public/build/manifest.json`).

### Configure `.env` (production values)

| Key | What to set |
|-----|-------------|
| `APP_NAME` | Business name |
| `APP_ENV` | `production` |
| `APP_DEBUG` | `false` |
| `APP_URL` | Full HTTPS URL, e.g. `https://www.yourdomain.com` (no trailing slash) |
| `APP_KEY` | Generated by `key:generate` — never commit this |
| `DB_*` | Production database credentials |
| `SESSION_DRIVER` | `database` (already default) or `redis` if available |
| `QUEUE_CONNECTION` | `database` (or `redis`) |
| `CACHE_STORE` | `file` or `redis` |
| `MAIL_*` | Real SMTP / mail provider (not `log`) |
| `MAIL_FROM_ADDRESS` / `MAIL_FROM_NAME` | Verified from-address for the domain |
| `RAZORPAY_KEY_ID` | Live or test key (optional) |
| `RAZORPAY_KEY_SECRET` | **Secret stays only in `.env`**, never in admin UI |
| `FILESYSTEM_DISK` | `local` is fine; public uploads use the `public` disk |

Also set matching values in **Admin → Booking Rules** for Razorpay Key ID + enable flag if you want online payments.

### Database, storage, and seed
```bash
php artisan migrate --force
php artisan db:seed --force          # first deploy only, if you want demo content + admin user
php artisan storage:link             # REQUIRED — service images & editor uploads
```

Permissions (typical shared/VPS layout):
```bash
chmod -R ug+rwx storage bootstrap/cache
# Ensure the web user owns or can write these directories
```

### Optimize Laravel for production
```bash
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan event:cache   # if available / used
```

### Web server
- Document root → `.../dscw/public`
- Force HTTPS
- Allow PHP to handle all non-file routes (Laravel default rewrite)
- Upload limits: allow at least **5MB** post body for service/editor images (`upload_max_filesize` / `post_max_size`)

### After go-live security
1. Log in to `/admin/login` and **change the admin password**
2. Confirm `APP_DEBUG=false`
3. Confirm `.env` is not web-accessible
4. Confirm `storage/` and `.env` are outside the public docroot (normal if docroot is `public/`)

## 2. Every future deploy (repeatable)

When you push new code to production:

```bash
php artisan down                    # optional maintenance mode
git pull                            # or upload release
composer install --no-dev --optimize-autoloader
npm ci && npm run build             # or upload public/build from CI
php artisan migrate --force
php artisan storage:link            # safe to re-run; no-op if link exists
php artisan optimize:clear
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan up
```

**Do not** re-run `db:seed` on every deploy — it can duplicate or overwrite content. Seed only on fresh environments (or use dedicated, idempotent seeders later).

## 3. Uploaded files (services + WYSIWYG)

| What | Where on disk | Public URL |
|------|----------------|------------|
| Service cover images | `storage/app/public/services/...` | `/storage/services/...` |
| Editor / description images | `storage/app/public/editor/...` | `/storage/editor/...` |

**Always keep `php artisan storage:link` working** so `public/storage` → `storage/app/public`.

Backups must include:
- The database
- `storage/app/public/` (all uploaded images)

Without that folder, service cards and rich-text images break after restore.

## 4. Payments (Razorpay)

1. Create Razorpay account; use **test** keys in staging, **live** keys only in production
2. Set `RAZORPAY_KEY_ID` + `RAZORPAY_KEY_SECRET` in `.env`
3. In Admin → **Booking Rules**: paste Key ID, enable Razorpay
4. Set webhook/callback URLs in Razorpay to your production domain when you add webhooks (future)
5. If keys are missing, customers only see **pay at location** — that is intentional

## 5. Mail, queues, and cron (needed as features grow)

Today many flows can run without a long-running queue worker. As you add emails, SMS, reports, or heavy jobs:

### Queue worker
```bash
php artisan queue:work --tries=3
```
Keep it alive with Supervisor / systemd / host panel “daemon”.

### Scheduler (Laravel cron)
Add one crontab entry:
```cron
* * * * * cd /path/to/dscw && php artisan schedule:run >> /dev/null 2>&1
```
Use this later for booking reminders, cleanup of expired holds, report digests, etc.

### Mail
Replace `MAIL_MAILER=log` with SMTP/API (SES, Postmark, Resend, host SMTP). Test booking + contact form emails after DNS SPF/DKIM are set.

## 7. Future features — deploy implications

These are not all built yet (many show as “soon” in admin). When they land, expect extra ops steps:

| Feature area | Extra production notes |
|--------------|------------------------|
| Blog / pages / FAQs / gallery CMS | More uploads under `storage/app/public/`; same `storage:link` |
| Media library | Possibly larger files; raise PHP upload limits; consider S3 (`AWS_*` in `.env`) later |
| Booking calendar / reports | May need queued jobs + cron |
| Email/SMS confirmations & reminders | Real `MAIL_*` / SMS provider keys; queue worker required |
| Coupons / marketing | Usually DB-only; clear caches after deploy |
| SEO tools | Sitemap generation may use scheduler |
| Users & roles / audit logs | Already partially present — keep DB backups |
| Multi-server hosting | Shared storage (S3) for uploads; Redis for cache/session/queue; sticky sessions or central session store |

When adding cloud file storage later:
- Set `AWS_*` (or equivalent) in `.env`
- Switch the `public` disk / upload services to S3
- Existing local files need a one-time migration

## 8. Local vs production differences (don’t copy blindly)

| Item | Local | Production |
|------|--------|------------|
| `APP_DEBUG` | `true` | `false` |
| `APP_ENV` | `local` | `production` |
| Database | Often SQLite | MySQL/Postgres |
| Mail | `log` | Real SMTP/API |
| Assets | `npm run dev` or build | Always built (`npm run build`) |
| Seeds | OK anytime | First deploy only |
| Razorpay | Test keys | Live keys |

## 10. Backups (ongoing)

At minimum, automate daily:
1. Database dump
2. `storage/app/public/` archive
3. Copy of `.env` stored **securely offline** (not in git)

Keep at least 7–30 days of retention depending on host.

## 11. Shared hosting — will it work?

**Yes, this Laravel app can run on typical shared hosting**, as long as the host meets the basics below. Many Indian shared hosts (cPanel / Plesk) work if you configure them carefully.

### What you need from the host
| Requirement | Why |
|-------------|-----|
| PHP **8.3+** (select in cPanel) | App requires PHP ^8.3 |
| MySQL / MariaDB database | Don’t use SQLite for production |
| Ability to set **document root** to the `public` folder (or map domain to `public_html` that *is* Laravel’s `public`) | Critical for security |
| Writable `storage/` and `bootstrap/cache/` | Logs, cache, sessions, uploads |
| **Symbolic links** allowed (`php artisan storage:link`) | Service & editor images |
| Cron jobs (optional but useful later) | Reminders / schedules |
| HTTPS (Let’s Encrypt) | Required for Razorpay & trust |

### What usually does *not* work well on shared hosting
- Running `npm` / Node on the server → **build assets on your Mac**, then upload `public/build/`
- Long-running `queue:work` daemons → use `QUEUE_CONNECTION=database` and either:
  - run jobs synchronously for now (or `sync` driver if you hit issues), or
  - trigger `php artisan queue:work --stop-when-empty` from a cron every minute
- Very large uploads / many concurrent bookings → shared CPU/RAM limits apply
- Multiple app servers / Redis → not needed yet; file/database drivers are fine

### Recommended shared-hosting layout
**Option A (best):** Upload the whole project *outside* `public_html`, then point the domain’s document root to `.../dscw/public`.

**Option B (common on cPanel):**  
1. Upload project to e.g. `~/dscw/`  
2. Copy (or symlink) contents of `dscw/public/` into `public_html/`  
3. Edit `public_html/index.php` so paths point to `~/dscw/` (vendor, bootstrap, storage)  
4. Keep `.env` inside `~/dscw/` (never inside a web-browsable folder)

### Shared hosting deploy steps (practical)
1. Create MySQL DB + user in cPanel  
2. Upload code (FTP/SFTP or Git if available)  
3. Upload already-built `public/build/` from your machine (`npm run build` locally)  
4. Create `.env` on the server with production values  
5. Via SSH (if available) or host terminal:
   ```bash
   composer install --no-dev --optimize-autoloader
   php artisan key:generate
   php artisan migrate --force
   php artisan db:seed --force    # first time only
   php artisan storage:link
   php artisan config:cache
   php artisan route:cache
   php artisan view:cache
   ```
6. If **no SSH**: some hosts offer “PHP Composer” and “Artisan” buttons; otherwise ask support to run `storage:link` and set permissions  
7. If symlinks are disabled: ask host to enable them, **or** mirror uploads into a real `public/storage` folder (workaround; prefer real symlink)

### Shared hosting verdict for *this* project today
| Feature | Shared hosting OK? |
|---------|-------------------|
| Public site + admin | Yes |
| Bookings + availability | Yes |
| Service images + Quill uploads | Yes **if** `storage:link` works |
| Razorpay | Yes (HTTPS required) |
| Email confirmations (later) | Yes with SMTP from host or Mailgun/etc. |
| Heavy queues / realtime | Prefer VPS later |

**Bottom line:** Shared hosting is fine for launch. Prefer a host that allows PHP 8.3, custom document root to `public`, SSH, and symlinks. If the host is very locked down (old PHP, no symlink, no Composer), use a cheap VPS or Laravel-friendly host instead.
